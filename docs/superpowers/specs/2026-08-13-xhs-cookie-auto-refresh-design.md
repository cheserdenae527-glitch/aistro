# 小红书 Cookie 池完整自愈方案 v2.3（扫码优先 + 半自动兜底 + 全自动检测）

> 日期：2026-08-13
> v2.3 变更（吸收第四轮评审，均为水位线补充链路细节）：
>  ①时效预算检查时点明确为「生成后、推送前」检查（杜绝先推后补救/用户收到两条码）
>  ②时效预算加重试上限（≤2 次），超限放弃自动补充→降级「仅预警+手动扫码」，失败可见
>  ③使用中锁定定死「借出/归还」显式标记，移除「时间窗口判定」备选（防慢速长任务被误判顶掉）
> v2.2 变更（吸收第三轮评审）：
>  ①水位线二维码时效管理（有效期预算/过期重生成/推送带时限提示/qrcode_expired 状态）
>  ②后端"有头浏览器"部署约束显式化（本机 GUI 满足；无 GUI 需 Xvfb 或改桌面端生成；B2 前最小 demo 验证）
>  ③淘汰跳过"使用中"锁定 Cookie
>  ④隔离退避（累计隔离次数翻倍 + 超阈值转人工）
>  ⑤去抖状态落库（last_trigger_ts 存 xhs_accounts）
>  阶段 A 已定稿（v2.1 阶段A不变）
> 定位：半自动为主（扫码需人工），全自动检测/补充为辅；不碰验证码自动化
> 状态：**定稿**（v2.3，2026-08-13 评审通过）

---

## 0. 总体策略

小红书「手机验证码登录后常要求扫码二次验证」的强风控下：
```
扫码优先（主路径） + 半自动人工兜底 + 全自动检测补充
```

| 层 | 机制 | 自动化程度 |
|---|---|---|
| 抓取 Cookie | Electron 有头扫码为主，Cookie 导入兜底，验证码登录可选（阶段C） | 半自动 |
| 检测失效 | 定时（30-60 分钟）+ 实时（爬虫失败回传） | 全自动 |
| 补充触发 | 水位线 → 推送二维码到通知（**含时效管理**）→ 人工扫 → 入库 | 半自动 |
| 池管理 | 本地文件池（现状）→ Redis（可选演进） | 全自动 |

## 1. 阶段 A（本期核心，已定稿 v2.1，本节不变）

### 1.1 桌面端（Electron）扫码登录窗口
- 独立 session（partition: 'xhs-login'，重登前 clearStorageData）；480×720 加载 xiaohongshu.com
- 轮询候选（每 2s）检测 `web_session` → **延迟 ~500ms** → verify（防时序竞态）
- verify 通过 = 真正登录成功（复用 check_cookie）；失败区分 reason
- 写入：新增（干净状态）或同账号替换；IPC 返回 {ok, action, reason}
- 超时 10 分钟关闭

### 1.2 后端 verify（挂 token）
```
POST /crawler/pool/cookies/verify   （鉴权）
body: { cookie }
→ check_cookie() → { ok, account_id, reason? }  // auth_incomplete | network_error
```

### 1.3 写入与替换
- `POST /crawler/pool/cookies`（新增）：干净健康度
- **池满 + 全新账号**：自动淘汰"健康度最低**且未被使用中锁定**"的一条（见下方锁定规则），提示淘汰了哪条；无可淘汰则报 pool_full
- **使用中锁定（定死实现方式）**：cookie 被 `acquire_cookie` 借出、尚未 `report_result` 归还时视为"使用中"；**淘汰候选跳过使用中的条目**，避免"正在爬的任务被扫码流程顶掉"
  - **实现定死为「借出/归还」显式标记**：`acquire_cookie` 选中时置位 `in_use=true`，`report_result` 归还时置 `in_use=false`；**不使用**"基于 last_used 后未 report 的时间窗口判定"——慢速长任务（分页抓取超窗口）会被误判为不在使用，反而造成"正在跑的任务被顶掉"，恰是本条要解决的并发问题的另一种形态
- **同账号替换**：按 account_id(=webId) 命中 → PATCH 替换 + 重置健康度（含 proxy_failures，粘性绑定合理）

### 1.4 前端
- 扫码按钮 + action 文案：ok/replace / cancel / timeout / token_expired / verify_failed(reason 细分) / rate_limited / pool_full
- 无桌面环境禁用；单条错峰预警（>24h 黄色单独提示；全失效才红警）

## 2. 阶段 B（增强）

### 2.1 账号池（PostgreSQL `xhs_accounts`）

```
字段：account_id(≡webId) / phone(可选) / status(正常|冻结|需验证|隔离)
      last_login_at / continuous_fail / quarantine_count / last_trigger_ts / remark
```

**标识统一**：account_id ≡ webId。

**状态机（含退避）**：
```
正常 →（失败累计3次）→ 隔离 →（退避到期）→ 正常 →（再失败）→ 隔离（恢复时间翻倍）→ ...
累计隔离 ≥3 次 → 转「需人工确认」，不再自动恢复（管理界面手动解除）
```
- **退避**：第 1 次隔离 24h 自动恢复；第 2 次 48h；第 3 次 96h；**累计 ≥3 次 → 转人工确认**（避免"僵尸账号"每 24h 空转一次，还伴随无效推送）
- 最短登录间隔 ≥30 分钟：**只约束系统自动触发**，用户手动扫码不受限
- **失败计数派生**：账号级 continuous_fail 从 cookie 失败事件同步（成功清零），不各算各的

### 2.2 Cookie 池（文件池现状，Redis 可选演进）

本地量级够；>10 账号/多实例再迁 Redis（Hash + Sorted Set）。

### 2.3 登录生成器（Cookie 来源）

| 方式 | 实现 | 说明 |
|---|---|---|
| 扫码登录（主） | Electron 登录窗口 | 有头；复用 Electron |
| 二维码推送通知 | 生成二维码 → POST 单人通道 | 见时效管理（2.5）与安全约束 |
| Cookie 导入 | 现有 add_cookie | 冷启动 |
| 手机验证码（C） | 可选 | 暂不设计 |

**安全约束（硬性）**：只允许单人可见通道（飞书单聊/企微单人应用/钉钉单聊），**禁群聊**；实现层校验 webhook 类型。

**有头浏览器部署约束（显式）**：
- 生成二维码需要**有头浏览器**（无头极易触发二次验证）
- 本项目为**本地桌面工具**：后端跑在本机（有 GUI 的 Windows），可运行有头浏览器（Playwright/Electron headful）——**满足**
- 若未来迁移到**无 GUI 服务器**：需引入 Xvfb 等虚拟显示，或改为"由桌面端生成二维码、后端只发通知信号"——**B2 排期前必须确认部署形态并做最小 demo 验证**，不默认"文档写完整 = 能跑"

### 2.4 健康检测器 + 补充信号

- 定时：CookieHealthScheduler 每 30-60 分钟 check_cookie → 失效冷却/淘汰
- 实时：爬虫失败回传 report_result → 账号级计数派生 → 触发补充信号
- **去抖（落库）**：`last_trigger_ts` 存 xhs_accounts 表字段；同账号触发补充信号后 **5 分钟内不重复**（重启不丢失，避免服务重启后短暂失去保护）

### 2.5 水位线自动补充（含二维码时效管理）

```
可用 Cookie 数 < 最低水位线:
    取健康账号（尊重 30 分钟系统间隔 + 隔离退避）
    → 生成二维码 → **时效预算（检查时点：生成后、推送前）**：
        - 定义二维码有效期 T（默认 3 分钟，可配）
        - 生成后**立即计时**；**推送前**检查生成至今耗时是否 > T×50%
        - 超时 → 丢弃本次、重新生成；**最多重试 2 次**
        - 确认耗时在预算内（≤T×50%）**才真正推送**（绝不"先推再补救"）
    → 推送（消息带"请在 {T} 分钟内扫码，过期可点重新生成"）
    → 等待人工扫码 → verify → 入库
```

**重试上限与降级**：
- 重试 ≥2 次仍无法在预算内推送（如 webhook 响应偏慢）→ **放弃本次自动补充**，降级为「仅预警 + 用户手动点扫码刷新」
- 本次失败**必须可见**：写日志（crawler.cookie_health）+ 管理界面/采集设置展示最近一次水位线补充结果（成功/重试后放弃），不默默重试到最后不了了之

**过期处理**：
- 新增 `action=qrcode_expired`：用户扫码/点链接发现码已过期 → 前端/通知提供「**重新生成**」入口，重新走生成-推送，不静默失败
- verify 若因二维码过期返回（reason=qr_expired）→ 同上

**架构约束**：水位线由后端定时任务触发，**只走推送二维码**（不依赖桌面在线）；"自动弹本机窗口"不做（或未来实时通道 + 降级）。

## 7. 验证清单

1. 扫码 → verify 通过 → 新增/替换（健康度干净）→ 搜索通过
2. 同账号再扫 → 替换刷新，无冷却残留
3. 游客假 cookie → auth_incomplete；verify 网络异常 → network_error
4. 扫码中关闭 → cancel；token 过期 → token_expired
5. 单条 >24h 错峰预警；全失效红警
6. **池满 + 全新账号 → 淘汰健康度最低且未使用中的一条并提示**；全部使用中 → pool_full
7. **正在使用的 cookie 不被淘汰**（并发安全）
8. （B1）隔离退避：第1/2/3次 24/48/96h，≥3 转人工；账号级计数随 cookie 失败同步
9. （B1）最短登录间隔只卡系统自动触发
10. （B2 demo）本地生成二维码 → 推送 → 扫码 → 入库，全链路 < 二维码有效期
11. （B2）水位线触发推单人通道；消息带时限提示；过期 action=qrcode_expired + 重新生成；5 分钟去抖（重启不丢）

## 8. 明确不做（所有阶段）

自动过滑块/验证码（违规）；完全无人值守；群聊 webhook 推二维码（劫持风险）；大规模养号。
